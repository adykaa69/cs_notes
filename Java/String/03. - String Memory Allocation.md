## 3.1 JVM Memory Overview
- From a `String` point of view, we only care about the **heap**.
	- Since **Java 7**, the **String Constant Pool (SCP)** is located **inside the heap**.
- Conceptually:
```
Heap
 ├── String Constant Pool (shared, deduplicated Strings)
 └── Regular heap objects (non-pooled Strings)
```
- Important:
- Stack memory does **not** store String objects  
- Variables only hold **references**
- Objects always live on the heap
## 3.2 String Constant Pool (SCP)
- The **String Constant Pool** is:
	- A JVM-managed cache of `String` objects 
	- Ensures **one unique String instance per value**
	- Shared across the entire JVM
- Rule:
	- If the same String literal already exists in the pool, Java reuses it instead of creating a new object.
	- This is only safe, because `String` is **[[immutable]] #todo**. 
## 3.3 String Literals and the Pool
> [!example]
> ```java
> String a = "hello";
> String b = "hello";
> ```
> > [!info] Memory model
> > ```
> > String Pool:
> >     "hello" <- a, b
> > ```
> 
> > [!info] Results
> > ```java
> > a == b; // true
> > a.equals(b); // true
> > ```
> - Both references point to the same **pooled object**
> - The pool guarantees reuse
> - String literals are pooled and shared.
## 3.4 `new String()` and Heap Allocation
> [!example]
> ```java
> String a = "hello";
> String b = new Strin("hello");
> ```
> > [!info] Memory model
> > ```
> > String Pool:
> >     "hello" <- a
> > Heap:
> >     "hello" <- b
> > ```
>
>> [!info] Results
>> ```java
>> a == b; // false
>> a.equals(b) // true
>> ```
> - `new String()`always creates a new object
> 	- even if the same value already exists in the pool
> 	- same content, different identities
### 3.4.1 Heap-only Strings
- Most Strings in real applications:
	- User input
	- File content
	- API responses
	- Database values
- These Strings:
	- Live on the **heap**
	- Are **not pooled**
	- Must **never** be compared using `==`
> [!example]
> ```java
> String input = scanner.nextLine();
> ```

## 3.5 Runtime vs Compile-Time String Creation
### 3.5.1 Runtime String Creation (Concatenation) 
> [!example]
> ```
> String a = "hello";
> String b = a + " world";
> ```
> > [!info] Memory model
> > ```
> > String Pool:
> >     "hello"
> >     " world"
> > Heap:
> >     "hello world"
> > ```
> 
> > [!info] Result
> > ```java
> > b == "hello world" // false
> > b.equals("hello world) // true
> > ```
> - Runtime concatenation uses `StringBuilder`
> - Result is **not pooled automatically**
### 3.5.2 Compile-Time String Creation
> [!example]
> ```java
> String a = "hello" + " world";
> ```
> Compiler optimization:
> ```java
> String a = "hello world";
> ```
> > [!info] Memory model
> > ```
> > String Pool:
> >     "hello world"
> > ```
> 
> > [!info] Results
> > ```java
> > a == "hello world"; // true
> > a.equals("hello world); // true
> > ```
> - Only [[02 - Creating Strings#Compile-time constants| compile-time constant expressions]] are pooled automatically.
## 3.6 `intern()` - Explicit Pool Management
- Rare
- Useful in memory-critical or canonicalization scenarios
> [!example]
> ```java
> String a = new String("hello");
> String b = a.intern();
> ```
> - Returns pooled instance if it exists
> - Otherwise adds the String to the pool
>> [!info] Memory model
>> ```
>> String Pool:
>>     "hello" <- b
>> Heap:
>>     "hello" <- a
>> ```
>
>> [!info] Results
>> ```java
>> a == b; // false
>> a.equals(b); // true
>> ```
## 3.7 `==` vs `equals()`
### 3.7.1 `==` operator
`a == b`
- Do both references point to the **same object**?
- Compares memory addresses
	- not content
### 3.7.2 `equals()` method
`a.equals(b)`
- Do both Strings contain the **same sequence of characters**?
- Content-based comparison
- Overridden by `String`

#### `equalsIgnoreCase()`
- Null-safe & flexible
`"yes".equalsIgnoreCase(input)`

### 3.7.3 Comparison Truth Table
|Scenario|`==`|`equals()`|
|---|---|---|
|Same pooled literal|true|true|
|Literal vs `new String()`|false|true|
|Two runtime-created Strings|false|true|
|Same reference|true|true|
